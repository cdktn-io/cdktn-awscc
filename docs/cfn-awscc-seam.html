One AWS CDK app, two synthesis targets: the CloudFormation template it was written for, or Terraform JSON built on awscc_* resources plus the cfncompat provider. This note measures the three places the seam actually binds — resource coverage, property-name casing, and nested values that dodge the generated mappers.

Where the 15% coverage gap lives

The gap is not one thing. It splits into three buckets with very different consequences for the bridge:

Bucket 1 — template-engine constructs (12): not a gap for the bridge

Seven AWS::Serverless::* types (the SAM transform) and five AWS::CloudFormation::* types (CustomResource, WaitCondition/Handle, Macro, ChangeSet). These are features of the CloudFormation engine, not provisionable cloud resources, so Cloud Control can never expose them. The bridge already owns them elsewhere: the custom-resource protocol is cfncompat_custom_resource (a faithful polyfill — Lambda/SNS service tokens, pre-signed S3 ResponseURL), while Fn::Transform/macros throw a clear synth-time error per RFC 002.

Bucket 2 — legacy and closed services (105): mostly noise

29 services have zero awscc coverage, and nearly all are deprecated, superseded, or closed to new customers: WAF Classic and WAFRegional, OpsWorks, Greengrass v1 (v2 is covered), Pinpoint and PinpointEmail, App Mesh, Cloud9, CodeCommit, CodeStar, the pre-OpenSearch Elasticsearch domain, Kinesis Analytics v1, MediaStore, SimpleDB, Device Farm, IoT Things Graph, Alexa ASK. AWS stopped investing before these ever got registry provisioning support. A handful still have aws-cdk-lib L2s; apps that use those can't bridge, which is an acceptable, documentable exclusion.

Bucket 3 — gaps in active services (137): the real edges

The bucket that actually bounds the bridge. Three patterns inside it deserve different handling:

  • Heavyweight resources missing outright. AWS::CloudFront::Distribution is the sharpest: awscc ships it as a read-only data source but not a resource, so the entire CloudFront L2 surface can't bridge. Alongside it: Cognito::UserPool, WAFv2::WebACL/RuleGroup, CodeBuild::Project, EKS::Nodegroup, FSx::FileSystem, EMR::Cluster, MediaLive::Channel, Glue::Table/Connection, DocDB and DAX clusters, DMS replication instances.
  • Pre-registry attachment & policy types. IAM::Policy (inline), SQS::QueuePolicy, SNS::TopicPolicy, IAM::AccessKey, EC2::NetworkAclEntry, Route53::RecordSetGroup, the RDS/ElastiCache/Redshift security-group trio. These use CFN's old resource model and never got Cloud Control semantics. They matter far beyond their count: every L2 grant*() call materializes a QueuePolicy/TopicPolicy, and RFC 002 already plans 1:N decomposition for IAM::Policy — this list says that pattern needs to generalize.
  • Sub-resource stragglers in otherwise-covered services: AppSync's GraphQLSchema/ApiKey, EC2's Client VPN family, Config's ConfigurationRecorder/DeliveryChannel, KinesisAnalyticsV2 outputs, LakeFormation permissions.

One curiosity runs the other way: exactly one awscc resource (awscc_datasync_storage_system) no longer exists in the CFN spec — a retired type the provider still carries.

Weighting the gap by actual L2 usage

Raw counts overstate the problem: a missing type only breaks the drop-in L2 bridge if hand-written aws-cdk-lib L2 code actually constructs its L1. And the 37 split again: 9 belong to deprecated L2 surfaces (all seven App Mesh types, CodeCommit::Repository, the pre-OpenSearch Elasticsearch::Domain) where breaking is acceptable and documentable — leaving 28 types in maintained L2s as the true drop-in blockers:

  • Widest blast radius: SQS::QueuePolicy and SNS::TopicPolicy — synthesized implicitly by nearly every grant*()/subscription pattern on queues and topics, not just by apps that "use" those modules.
  • Whole-module blockers: CloudFront::Distribution (the entire CloudFront L2), Cognito::UserPool, CodeBuild::Project/ReportGroup/SourceCredential, EKS::Nodegroup, FSx::FileSystem, DocDB's cluster/instance/parameter-group trio.
  • Feature-path blockers: EC2's Client-VPN family (4 types) plus NetworkAclEntry and VPNGatewayRoutePropagation, ElasticLoadBalancingV2::ListenerCertificate, IAM::AccessKey/UserToGroupAddition, SES::ReceiptRule, ServiceDiscovery::HttpNamespace/Instance, Logs::Transformer, AppSync::ApiKey/GraphQLSchema, BedrockAgentCore::GatewayTarget.

Read for the bridge: the honest coverage number for unmodified L2 apps is far better than 85.5% — the engine bucket is already polyfilled, the legacy bucket is mostly dead L2 surface, and the L2-usage weighting narrows the real blocker list to 28 maintained-L2 types, headed by the implicit QueuePolicy/TopicPolicy pair that grant*() patterns synthesize everywhere. Those 28 need per-resource decisions (decompose, map to the aws provider, or refuse loudly) before Phase 2 promises drop-in behaviour; the other 212 missing types only matter to apps instantiating L1s directly. (WAFv2's WebACL/RuleGroup are L1-only by this measure — no maintained L2 constructs them — yet common enough in real apps to deserve a decision anyway.)

Three spellings, two safe round trips, one hard crossing

How PascalCase vs snake_case is handled by the two generators — and why the bridge can't compute its way across.

Every property has up to three spellings: the CFN registry's PascalCase, the TypeScript prop's camelCase, and the awscc attribute's snake_case. Each generator is safe because it never converts at synth time — it looks up the spelling it recorded at codegen time:

GeneratorCodegen directionSynth direction
spec2cdk (CFN L1s, aws-cdk-lib) Registry PascalCase → camelCase via propertyNameFromCloudFormation, with hand-curated quirk rules (ProviderARNs→providerArns, MBs, AZs, GetObject…) renderProperties maps each prop back to the original spec spelling — a lookup, not a re-conversion. Template gets exact registry names.
awscc2cdk (@cdktn/awscc) awscc schema snake_case → camelCase via codemaker's toCamelCase — mechanical and safe, because snake_case marks every word boundary. (The quirky step happened upstream, when AWS's provider generator derived ipv_4_ipam_pool_id from Ipv4IpamPoolId.) synthesizeAttributes() and the struct mappers emit the schema spelling verbatim — again a lookup. The naming spike confirmed zero of spec2cdk's sanitizers are needed on this input.

The ipv_4_* counter-example

The bridge is the one place that must cross from the CFN spelling to the awscc spelling with no recorded pair in hand — an inline literal in aws-cdk-lib carries only its PascalCase keys. That crossing cannot be computed in either direction:

// CFN registry / aws-cdk-lib literal
Ipv4IpamPoolId
// what the awscc schema actually requires (AWS's own derivation)
ipv_4_ipam_pool_id     — schema.json: ipv_4_address, ipv_4_netmask_length, ipv_6_cidr_block, …
// what any naive PascalCase→snake_case gives — rejected by the provider
ipv4_ipam_pool_id

And the camelCase forms prove the deeper point — both worlds camelCase to the same string:

CFN registryaws-cdk-lib prop@cdktn/awscc propawscc attribute
Ipv4IpamPoolIdipv4IpamPoolIdipv4IpamPoolIdipv_4_ipam_pool_id
EncryptionTypeencryptionTypeencryptionTypeencryption_type

Identical camelCase, different snake_case: the underscore positions are information that only the awscc schema holds, and camelCase destroys it. So no string function recovers ipv_4_ipam_pool_id from either Ipv4IpamPoolId or ipv4IpamPoolId — the map must be emitted by codegen, and @cdktn/awscc is the only component that owns both spellings. That resolves RFC 002 §9 Q3: we don't wait for AWS to populate cfnPropertyNames; the generator exports its own per-resource CFN-name→attribute map.

The direction the issue missed: PascalCase → camelCase is quirky too

The generated struct mappers (ccVPCVpcEncryptionControlPropertyToTerraform, …) are exported today — but they take camelCase keys. An intrinsic-embedded literal from aws-cdk-lib arrives in PascalCase, and lowering the first letter is not a conversion either: Ipv4, IPv6, LoRaWAN, ARNs all break it (spec2cdk needs a hand-curated suffix table for exactly this). Keying the emitted map by the CFN PascalCase spelling makes the whole question disappear — one lookup instead of two conversions.

Nested values that dodge the mappers

How struct translation works at synth time — and the exact mechanism by which Lazy values and intrinsic arguments skip it.

In generated cdktn-style code, every nested struct gets a camelCase interface plus a mapper that rewrites one level of keys to the schema spelling; synthesizeAttributes() composes them over the resolved value tree at synth time. The escape hatch is in the mapper's very first line:

// generated/aws-ec2/vpc.ts — every generated mapper opens with this guard
export function ccVPCVpcEncryptionControlPropertyToTerraform(struct?) {
  if (!cdktn.canInspect(struct) || cdktn.Tokenization.isResolvable(struct)) {
    return struct;  // an IResolvable passes through with its keys untouched
  }
  return { egress_only_internet_gateway_exclusion: cdktn.stringToTerraform(struct!.egressOnlyInternetGatewayExclusion) };
}

Key mapping happens at attribute-collection time, but token resolution happens later. So any value that reaches a struct-typed slot as an IResolvable — a Lazy.anyValue({ produce }), or an object handed straight to a provider function — is returned verbatim by the guard, and when it finally resolves, its keys are rendered as written. Nothing converts them to snake_case. This is the gotcha confirmed in cdktn today, no CFN involved: the produced object lands in *.tf.json with camelCase (or PascalCase) keys and the provider rejects the plan.

The same shape reproduces one level up in the bridge, from real, unmodified aws-cdk-lib source:

// aws-cdk-lib/aws-kinesis/lib/stream.ts:1005-1007 — parseEncryption()
streamEncryption: Fn.conditionIf(conditionName, Aws.NO_VALUE,
  { EncryptionType: 'KMS', KeyId: 'alias/aws/kinesis' })  // CFN PascalCase bag

// lowers to a cfncompat call — rendered verbatim, awscc_kinesis_stream rejects it:
provider::cfncompat::condition_if(cond, null, { EncryptionType, KeyId })
// the schema wants: { encryption_type, key_id }

No codemod fixes this: the Phase-2 rewrite touches constructors, not literals, and no Cc* type is even in scope at that call site. It has to work automatically or the "byte-identical, zero-modification" promise fails.

Today's pattern, and the systematic fix

The working pattern today is to run the value through the resource's own exported mapper before it leaves typed land — typed input, and immune to schema renames:

// WRONG — hand-written snake_case: untyped, silently breaks on schema renames
conditionIf(cond, null, { encryption_type: "KMS", key_id: "alias/aws/kinesis" })

// RIGHT — reuse the generated mapper: tsc checks the keys, codegen owns the renames
conditionIf(cond, null,
  kinesisStreamStreamEncryptionToTerraform({ encryptionType: "KMS", keyId: "alias/aws/kinesis" }))

That works when a human writes the call. The bridge can't ask aws-cdk-lib to change, so the systematic version is the shared map from §2, applied in two places:

  • TerraformIntrinsicResolver, recursively: while lowering an intrinsic, walk any embedded object literal and translate each key through the per-resource CFN-name→attribute map — the same shared export AwsccL1Renderer uses for the top-level Properties walk, never renderer-internal state.
  • Resolve-time fallback: for Lazy-produced values, the mapper can't run early by definition — the still-open spike question (plan §8) is whether these literals are statically detectable at all, or whether the resolver must walk unknown object literals at resolve time.
