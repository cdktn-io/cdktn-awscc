The Key-Map Decision

Should emitCfnPropertyMap ship on? What the flag actually changes at each stage of the library's life — generation, publish, import, synth, and the Phase-2 bridge — with the costs on one side and the one thing only this feature can do on the other.

flag: emitCfnPropertyMap · default OFF PR #3 @ 4f691fc full builds measured 2026-08-31 (both states, go/python/js)

First, the misconception to kill: the map is not an alternative to the case-converter mappers. With the flag on or off, synthesizeAttributes() translates properties through the generated *ToTerraform functions, exactly as today — the static is never read during synthesis. It is an additional, passive lookup table for external consumers: the Phase-2 bridge's intrinsic resolver, and any non-TypeScript code that needs the CFN↔terraform spelling pairs (which the mappers cannot provide, since jsii drops exported functions from every non-TS language).

The benefit ledger

  • It is the only cross-language spelling oracle. The exported *ToTerraform mappers never enter the jsii assembly (verified: 7,789 in the JS, 0 in the assembly; none reachable from the published Python package) — a static is the only shape Python/Java/.NET/Go can see.
  • It works where the mappers can't run. The mappers execute at synth-time attribute collection and pass IResolvable/Lazy values through untouched; a lookup table has no such timing — the bridge (or any resolver) can consult it at resolve time, on values the mappers never saw.
  • It is what the byte-identical bridge promise needs. Unmodified aws-cdk-lib embeds CFN PascalCase property bags inside intrinsic calls; the codemod can't rewrite literals, and the translation isn't computable (Ipv4IpamPoolId → ipv_4_ipam_pool_id). Recursive lookup over this map is the mechanism RFC 002 now specifies for TerraformIntrinsicResolver.
  • Off costs nothing, on costs nothing at synth. Flag off is byte-identical to pre-feature output (contract-tested); flag on adds no reader to any hot path.
  • The data is clean. Pre-study over the full schema: 30,674 pairs, zero conflicts globally and per-resource — the flat merged shape loses nothing, and a future consolidation (one global map) stays possible.

Alternatives if the size numbers disappoint

AlternativeTrade
Sidecar JSON in the npm package only (a data file, excluded from jsii) Near-zero cost for Go/Python/Java/.NET packages. Sufficient if the only consumer is the TypeScript-side bridge (@cdktn/aws-cdk-terraform-provider is TS); gives up the map for non-TS app authors hand-writing intrinsic literals — the audience the cdktn-planning#1 demo showed exists.
Companion package (e.g. @cdktn/awscc-cfn-names, jsii-built, maps only) Core packages stay at today's size in every language; bridge adds one dependency it already conceptually has. Costs a second release pipeline and version-lockstep discipline with the provider schema.
Per-module opt-in (emit maps only for modules the bridge targets first) Cheap start, but creates a "which resources have maps" matrix that leaks into the bridge's error handling.

Recommendation

Ship v0.1.0 with the flag off (it already is — and there is deliberately no CLI toggle in generate-all.ts, so it cannot flip on by accident). The measured numbers remove size as a blocker: every artifact grows ~1–4% (Go module zip +0.7%, at ~16% of the 500 MiB limit with ~6× headroom), runtime cost is confined to module load, scales with modules actually imported, and rounds to zero for realistic apps — synth is verifiably untouched. What remains is the API-commitment question, not a size question: enabling publishes the map's keying and shape as public cross-language API while the read-only-attributes and global-vs-per-resource design questions are still open. So: enable at Phase-2 kickoff in a coordinated release, after settling those two questions — or, if the bridge remains the sole consumer by then, take the sidecar-JSON route and keep the jsii surface unchanged.
